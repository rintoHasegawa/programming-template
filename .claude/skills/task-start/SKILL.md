あなたはタスク着手の司令塔です．着手準備（アサイン・ボード操作・作業ブランチ作成）の実行は **ops-runner エージェント**（軽量モデル）に委譲し，あなた自身はユーザー確認の仲介・Issue 内容の見極め・`/implement` への引き継ぎを行います（使用量節約のため，git・gh 操作を自分では行わない）．

本スキルは **solo / team 両モードで使用できる**．team モードでは GUIDE_03（チーム開発ルール）にも従うこと．solo モードでは GUIDE_03 は存在しないため，本スキルと本スキルの `reference.md` の記述を基準とする．

本コマンドは既存 Issue から作業を始めるためのものです．新規 Issue を立てる場合は `/task-create` を使ってください．Issue 無しで小さい変更や試験的作業を進める場合はこのコマンドは不要です．

## ステップ 1: 前提確認 (Pre-check)

$ARGUMENTS を確認する．

- Issue 番号（数値または `#数値`）が指定されていなければ「対象の Issue 番号を指定してください．新規 Issue を立てる場合は `/task-create` を使います」と伝えて終了する
- `--prep-only` が指定されていれば，着手準備（ステップ 2〜3）だけを行い，ステップ 4 の見極めと `/implement` への移行はせずにステップ 5 の完了サマリーで終了する

## ステップ 2: 委譲 (Delegate)

ops-runner エージェントを起動し，プロンプトに以下を含める:

- 手順書: 本スキルの `reference.md`（`.claude/skills/task-start/reference.md`）の「/task-start 実行手順」を読んで従うこと
- 対象の Issue 番号
- **ブランチ名**: Issue の内容を把握している場合（同セッションで `/task-create` した直後等）は `.claude/rules/git-conventions.md` の命名規則で決めて渡す．把握していなければ ops-runner に規約どおり提案・作成させ，報告で名前を確認する
- 確認が必要な事態（未コミット変更・未マージブランチ・進行中タスクあり・他人アサイン等）では，該当項目をまとめて停止・報告すること
- 報告には Issue の本文とコメント（`/task-handoff` の引継ぎメモを含む）を**要約せずそのまま**含めること

## ステップ 3: 確認の仲介 (Confirm)

エージェントが確認事項で停止した場合は，状況をユーザーに提示して判断を仰ぎ，承認された項目を「ユーザー承認済み」と明示して再委譲する．

## ステップ 4: 着手判定 (Readiness Check)

ops-runner の報告に含まれる Issue の本文・コメントを読み，関連する仕様・設計ドキュメント（`docs/` 配下等）を必要な範囲で確認したうえで，**実装に入る前に人間の判断が必要な点**を洗い出す．洗い出した結果により，以下の 3 つに分岐する．

| 判定 | 基準 | 動作 |
| --- | --- | --- |
| A. そのまま実装可 | 目的・完了条件・実装方針が Issue と既存ドキュメントから読み取れる．細部はコードベースの慣習や妥当な既定で決められる | 確認せずに `/implement` へ進む |
| B. 数問の質問で解消 | 未決事項が少数（目安 4 問以内）で，それぞれ選択肢を示して答えられる粒度である（例: 2 案のどちらで実装するか，表示文言，対象範囲の線引き） | `AskUserQuestion` で 1 回にまとめて質問し，回答を反映して `/implement` へ進む |
| C. 会話で詰める必要あり | 要件・目的そのものが曖昧，複数の設計方針に大きなトレードオフがあり議論が要る，Issue に「要検討」「相談」等の記載がある，不可逆な判断（スキーマ・公開 API・外部サービスの選定等）を含む，質問が 4 問を超える | 停止する（下記） |

判定の注意:

- 迷ったら B に倒す（推測で実装に入って手戻りするより，数問聞く方が安い）．ただし規約・既存ドキュメントで既に決まっている事項，すぐ決まる二択で推奨が明確な事項は質問しない（推奨を採用し，`/implement` へ渡すタスク内容に「採用した前提」として明記する）
- B の質問は，各問に推奨案を先頭（`(Recommended)` 付き）に置き，Issue の該当箇所を引用して単独で読めるようにする．回答で新たな大きな論点が出てきた場合は C に切り替える
- C で停止する場合は，ステップ 5 の完了サマリーに続けて「決める必要がある論点」（論点・背景・考えられる選択肢と推奨）を提示し，会話で方針を詰める．合意できたら，ユーザーの「進めて」等の指示を受けて合意内容を反映した `/implement` に進む（ユーザーの再入力は不要）
- 不可逆な設計判断で自信が持てない場合は，C で停止する前に `/consult` の利用を検討してよい（`consult` skill の利用条件に従う）

## ステップ 5: 完了サマリー (Summary)

ops-runner の報告をもとに以下を提示する（A・B では `/implement` に進む直前に簡潔に提示する）:

- **Issue**: 番号・タイトル・URL
- **ボード**: In Progress（`.claude/project-board` が無い場合は「アサインのみ（ボード未使用）」と表記する）
- **ブランチ**: 作成したブランチ名
- **着手判定**: A / B / C と，その理由 1 行（B の場合は質問と回答の要約，`--prep-only` の場合は「着手準備のみ」）
- **次の手順**:
  - A・B: 「`/implement` を開始します．」
  - C: 「上記の論点を決めたら `/implement` に進みます．」
  - `--prep-only`: 「`/implement` に対象 Issue の内容を渡して実装を開始してください（`gh issue view <Issue番号>` で取得できます）．」

## ステップ 6: 実装への移行 (Hand Off to Implement)

A・B（および C で合意した後）は，Skill ツールで `implement` skill を起動する．引数（タスク内容）には以下を含める:

- Issue 番号・タイトル・URL
- Issue の本文（コメントに仕様の追記・引継ぎメモがあればその要点も）
- B の質問への回答・C で合意した内容・判定時に採用した前提（「確定事項」として明記する）

以降は `implement` skill の手順（Phase 1 後の人間による動作確認等）に従う．`/implement` の完了後もコミットは行わず，`/commit` を案内するだけにする（CLAUDE.md「Git 運用」）．

## 注意事項 (Notes)

- branch↔Issue の紐付けは，後の PR 本文の `Closes #<Issue番号>` で行う．ブランチ名には番号を入れない
- Projects（ボード）は既定では使わず，`.claude/project-board` があるときだけ操作する（`reference.md`「ボード設定の判定」）
- `.claude/project-board` がある場合に限り `project` スコープが必要．スコープエラーの停止報告が来たら `gh auth refresh -s project` をユーザーに案内する（`reference.md`「必要なスコープ」）
- 新規 Issue を立てる場合は `/task-create`，Issue 無しで進める場合は本コマンドを使わず直接 `/implement` 等へ
- 着手準備だけ行い実装は後で始めたい場合は `--prep-only` を付ける
